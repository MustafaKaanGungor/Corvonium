Code review · after block two

Corvonium Block Two Review

Task view is complete against §3.4 and the derived-state architecture is holding up under real code. But three of the data model's core capabilities have no interface yet, and one whole section of the screen can never contain anything.

Reviewed 16 source files 42 tests, all passing Typecheck & lint clean 17 findings

What exists

Two packages in a pnpm workspace. packages/shared holds the domain layer — types and pure rules, no React, no RxDB, no browser. apps/web holds everything platform-specific. The boundary is real: the shared tests run in about 300 ms with no DOM and no mocks, which is only possible because the logic under test does not know those things exist.

shared/ types · derive · create · transitions · grouping · filters · ordering └── pure functions of (data, now). No I/O. web/db/ schema/ the runtime contract, checked by ajv in dev database lazy singleton, RxDB + Dexie + migrations hooks reactive queries → React items the impure edge: the clock and the id generator web/lib/ useNow the one place that reads the clock format Intl, display only web/features/ tasks/ the matrix, two filter axes, drag and drop items/ the row and the shared editor

The loop nothing in the code connects

A click calls addItem, which writes to IndexedDB. Nothing then tells the list to update — the list subscribed once, in an effect, and RxDB pushes to it. That is why a second browser tab reflows without a line of code written for it, and why a sync push in Phase 2 will arrive through the same path.

Three rules the code now encodes

Impurity lives at the edges. createItem(input, now, id) and isMissed(item, now) receive time rather than reading it. The only place in the item path that reaches out to the world is addItem.

Derived, never stored. There is no missed column, no urgent column, no priority. A test asserts the design claim directly: the same item, unchanged, changes matrix group as the clock advances.

Exactly one place reads the clock. useNow ticks once a minute and everything receives it. The second rule is only true because of the third — derived state computed from a frozen timestamp is stored state with extra steps.

Findings · bites now

01
Structural

The Routine group can never contain anything

Routine membership is rrule !== null, and nothing in the interface can set rrule. The editor has fields for title, notes, due, important and project — that is all. So the first of the five matrix groups renders Nothing here permanently, and will until recurrence ships in block five.

Not a bug in the code so much as a section of UI shipped ahead of the feature that fills it. Worth knowing it is empty by construction, not by accident.

features/items/ItemForm.tsx · grouping.ts

02
Structural

There is no way to create an event

kind defaults to 'task' in createItem and the form never sets it. Every item in the database is a task.

Core principle §1.5 is "tasks and events are the same thing" — the decision the whole model rests on. It is faithfully implemented in the data layer and has no expression in the interface at all.

shared/create.ts · features/items/ItemForm.tsx

03
Structural

No timed blocks, no all-day items

start, end, startDate, endDate and allDay are in the type, in the schema, and handled by isMissed — but no form field writes any of them. Only due is reachable.

This one has a deadline attached: the calendar in block six draws bricks from start/end spans. Built today it would render an empty grid, because no item can have a span.

features/items/ItemForm.tsx · §2.1

04
Correctness

The type and the schema disagree about notes

types.ts declares notes?: string — optional. The RxDB schema lists notes in required. TypeScript will therefore accept an item the runtime validator rejects.

Nothing triggers it today because createItem always supplies a value, so it sits waiting for the first code path that omits one. The fix is one character: notes is non-optional, for the reason §6 gives — "" already means "no notes", so a second way to say the same thing is pure cost.

shared/types.ts:6 · db/schema/items.ts (required)

05
Correctness

Loading and failure both render as nothing

{items && <TaskView …>} — when items is null, nothing renders. The Loading… and No items yet states were lost when TaskView replaced the original list.

useItems returns null both while opening the database and forever after it fails to open, so a genuine failure is indistinguishable from a fast load: a blank column and a message in the console. That is precisely the silent hang the .catch() was added to prevent, reintroduced one layer up.

Findings · architecture

06
Layering

Project writes live inside a schema file

addProject and removeProject are defined in db/schema/projects.ts, next to the JSON Schema. Items follow the intended shape — schema in db/schema/items.ts, writes in db/items.ts — so the two collections are organised differently for no reason.

It reads oddly in App.tsx too: import { addProject } from './db/schema/projects'. Three more collections are coming; the pattern should be settled before it is copied three times.

db/schema/projects.ts → should be db/projects.ts

07
Duplication

useItems and useProjects are the same function twice

Thirty lines each, differing only in the collection name and the type parameter. Two copies is not yet evidence of the right abstraction — but subtasks, sessions and settings are all coming, and a fifth copy is not a judgement call any more.

A single useCollection(name) would carry the loading contract, the unsubscribe, the cancellation guard and the error handler in one place, so a fix to any of them lands everywhere.

db/hooks.ts

08
Staleness

The edit sheet holds a snapshot, not a subscription

editing stores the Item object captured at click time and never refreshes from the live query. Everything else in the app reads through a subscription; the editor is the one surface that does not.

Harmless with one device and one tab. It becomes wrong the moment Phase 2 sync can deliver a change while the sheet is open — the form would then save a draft built on data the database has already moved past.

Findings · specification gaps

12
Behaviour

All-day items are invisible to urgency and to "This week"

Both isUrgent and the this-week filter begin with due !== null. An all-day item carries startDate, not due, so it is never urgent and never appears under This week.

For urgency this matches §3.4 exactly — "an item with no due date is never urgent". For the filter it is harder to defend: a filter named after a span of time silently omits items that fall inside it. isMissed already handles the all-day case; these two do not.

Deferred

urgentWithinDays is a constant in a component

Hard-coded as 2 in TaskView.tsx with a comment, because the settings document has no UI. Correct for now; it needs to move when Settings lands, and it is the only tunable in the app that currently cannot be tuned.

features/tasks/TaskView.tsx:34

14
Behaviour

Deleting a project leaves items pointing at it

Nothing clears projectId on the affected items. The colour dot simply stops rendering, because the lookup returns undefined — so it degrades quietly rather than breaking. The project filter already self-heals for the same reason.

Arguably correct for an offline-first app: a hard cascade would be a multi-document write racing against sync. Worth deciding deliberately rather than discovering later.

Findings · scale and testing

15
Scale

Every insert reads the entire collection

addItem calls db.items.find().exec() to compute keyAtTop. That is every item, loaded and mapped, on every add.

Invisible at a few hundred items and worth knowing about at a few thousand. A sorted query limited to one row would give the same answer — the minimum key is all it needs.

db/items.ts (addItem)

16
Coverage

apps/web has no test runner

All 42 tests live in packages/shared. Nothing covers resolveDrop — the function deciding where a dragged item lands and whether a drop is legal at all — nor any component.

This is also why grouping.ts and filters.ts sit in shared despite the server having no use for them: it was the only place they would be tested. Tooling shaped the architecture, which is worth naming.

What I would fix first

  1. Restore the loading and error states. Ten minutes, and it stops the next database problem from presenting as a blank screen. — 05
  2. Make notes non-optional and drop the stale 'deleted' omit. Two characters; closes a type-versus-runtime disagreement before something walks into it. — 04, 11
  3. Move project writes to db/projects.ts and add deletion. Settles the collection pattern before three more copy it. — 06, 10
  4. Extend the item form: kind, all-day, start and end. The largest gap and the one with a deadline — the calendar cannot be built against a model no item can populate. — 02, 03
  5. Add Vitest to apps/web and test resolveDrop. The drag logic is the most intricate code in the app and the only significant piece with no coverage. — 16

Findings 07, 08, 09, 12, 13, 14 and 17 are real but not urgent. Two of them — the duplicated hooks and the stale editor snapshot — become materially worse in Phase 2 rather than now, which is the right time to revisit them.
